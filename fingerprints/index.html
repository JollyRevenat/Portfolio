SPECIMEN CARD / AI-GENERATED WEB APPLICATIONS

Do AI models leave fingerprints in the security of the sites they build?

I gave different AI coding models the same specification for the same web app, then tested every finished site for the same security weaknesses. This is what happened, including the parts that did not work.

AQUESTION

Frontends often look AI-made. What about the code you cannot see?

People have started to recognize AI-built sites by how they look. I wanted to know whether something similar exists underneath, in security decisions. If a model keeps making the same mistakes, those mistakes could work like a fingerprint.

The main question: when different models independently build the same full-stack app under the same conditions, do they show repeatable, model-specific patterns in their security weaknesses? A side question grew from it: is there one universal flag that marks a weak AI-made site from the outside?

BMETHOD

Same app, same tests, different builder

Every model builds ProjectHub, a project-management app with accounts, roles, tasks and file uploads. Each gets the same prompt, the same files and the same tools, and only generic functional feedback. No model is told anything about security.

A site counts as finished only when it passes the functional checks. Its source is then frozen and never repaired. Next, a fresh evaluator that does not know which model built the site goes through a fixed 35-item weakness checklist. I re-test the important findings live on a fresh copy.

The sites are intentionally left unhardened, so they only ever run on my own lab machines and are never put on the public internet.

DFINDINGS

What the sites got wrong

Darker cells mean a larger share of that model's sites. Nemotron has only 3 sites, so its shares move in big steps.

Across all 23 sites I confirmed no injection flaws, though one Nemotron site served uploaded files in a way that allowed stored XSS. Most weaknesses cluster in things the functional tests never check, such as session secrets, rate limits and security headers. Models build what gets tested.

Some items do differ by model. All 10 Haiku sites set a SameSite cookie, while 7 of 10 Sonnet sites and all 3 Nemotron sites left it out. This is an early hint, not a result: the samples are small and the Sonnet and Haiku evaluators had different tools.

EUNIVERSAL FLAG
NOT FOUND

The search for one sign that gives a weak AI site away

The idea was simple and useful: find something visible from outside a site that shows up on AI-built sites and also goes along with real weaknesses. A real flag has to pass three tests. It recurs across sites, it comes from the AI and not from my setup, and anyone can see it from outside.

I checked public signals on the 3 Nemotron sites: pages, headers, cookies and the 404 page. The evaluation labels were saved first, so this search could not influence them. Items from the checklist cover all 23 sites. None of the 9 candidates passed all three tests.

Everything that recurred traces back to how my lab runs the sites, or to the spec itself. The page markup, where a model's own habits could show, varied from build to build.

This negative result is useful, but it is not proof that no flag exists. It tells me what a real test needs: more models, the same public check on every set, a different hosting setup, and human-written sites to compare against.

FPROCESS

How it was built

GHOW I WORKED

I set the research question, made the methods decisions and approved every run. AI agents did much of the implementation and analysis under my direction, including Claude Code and Codex. I kept them separate from the generators, so no model building a site could see the research plan.

Everything is logged: decisions, source hashes, failed attempts and the fixes that followed. Failures stay in the record because they are part of what the project found.

HLIMITS AND NEXT

This is exploratory work and leaves out final statistics. It has 3 models, small samples and one evaluator per site. The checklist is a pilot, and the evaluator setup changed between the Sonnet and Haiku sets. The count of 23 leaves out earlier calibration runs, one GPT-5.6 Sol site that was validated separately, and the Haiku 4.5 and GPT-6 Luna runs that began on Nov 2. I cannot yet claim that fingerprints exist.

Next: finish the Haiku 4.5 set, get a Codex set working, run the same public check on every set, try another hosting setup, and add human-written sites to compare against.
